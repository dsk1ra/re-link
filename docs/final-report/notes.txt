Re:Link is a Flutter client plus a Rust signaling server backed by Redis for blind rendezvous. The client handles onboarding, invite generation, pairing UX, and part of the media stack in Dart, while a flutter_rust_bridge crate provides the shared-signaling crypto, the base data-channel WebRTC session, and the active file-transfer implementation in Rust. The shared Rust crate holds the common cryptographic helpers and message DTOs used across the project.
The deployment assets are containerized: a Rust signaling server, Redis, Caddy as reverse proxy and TLS terminator, and an optional coturn service. In the checked-in docker-compose file, coturn defaults to STUN-only; TURN mode needs extra credentials and relay-port configuration. Windows client packaging is handled separately with Inno Setup.
Client Side

App startup can reset SharedPreferences when requested, initializes logging, initializes the Rust bridge, then loads local settings and chooses between the welcome flow and the main pairing screen. A wrapper also re-creates the HTTP signaling backend when the configured domain changes, although the active pairing flow mostly talks to the server through ConnectionService rather than through that backend abstraction.
Onboarding and persistence store the signaling domain, optional separate ICE host, optional custom ICE-server JSON, and the welcome-shown flag. The settings layer normalizes domains, generates a default STUN entry from the signaling or ICE host, and sanitizes user-provided ICE JSON into the shape expected by flutter_webrtc.
The first-run UI collects the server address, optional public ICE host, and ICE server config, then marks onboarding complete. The main pairing screen probes /health, surfaces reachability, and routes the user to initiator or responder flows.
The initiator flow generates the rendezvous token and shared secret locally in Rust, asks the server to allocate a mailbox, creates the invite link, and waits for the first mailbox event before showing an approval dialog. After acceptance it starts the base WebRTC handshake, then layers on session liveness, file transfer, and optional screen sharing. The responder flow parses the invite link, can switch to the server URL embedded in that link, derives the same signaling key material from the secret fragment, joins the mailbox, and starts the complementary WebRTC flow.
There is still a small HTTP registration/heartbeat abstraction in HttpSignalingBackend. It stores a client id and session token and keeps a heartbeat timer alive, but it is not part of the live pairing path: the current signaling server does not expose /register or /heartbeat, and the initiator/responder pages do not call that abstraction.
The active blind-rendezvous client logic lives in ConnectionService. It generates local pairing material through Rust helpers, posts /connection/init and /connection/join, encrypts and decrypts signaling payloads end-to-end, fetches mailbox history, subscribes to websocket push updates, retries send requests on transient failures, and reconnects the mailbox websocket with capped exponential backoff.
The pairing-code helper turns the SAS into a grouped 9-digit human-verifiable code, with grouped uppercase hex as a fallback for invalid input.
Session liveness is handled in Dart with a lightweight heartbeat protocol: send ping every 5 seconds, treat more than 15 seconds without a pong as timeout, send a local session_closed control message with a 5-second ack timer, and stop timers during teardown.
Ordering of async work is handled by a serial task queue. It guarantees one-at-a-time processing, supports clearing pending work, and swallows per-item failures unless an error handler is installed.
File transfer on the Dart side is a polling wrapper over Rust state rather than a direct native callback stream. It initializes the Rust transfer actor for a connection, drains queued Rust state updates on a timer, maps them into UI state, picks a default save directory by platform, and forwards send, accept, reject, and cancel actions into Rust.
WebRTC responsibilities are split. The base peer-connection session, control channel, file-transfer channel, ICE candidate emission, and control/file message events are managed by the Rust bridge and drained into Dart on a poll loop. Screen capture, desktop source enumeration, the separate media peer connection used for screen sharing, remote media rendering, and adaptive quality adjustments are handled in Dart with flutter_webrtc.
The Flutter package declares the expected transport and persistence dependencies such as flutter_rust_bridge, flutter_webrtc, http, web_socket_channel, shared_preferences, path_provider, file_selector, desktop_drop, share_plus, logging, freezed, and integration_test, but there are also a few apparent leftovers such as qr_flutter, file_picker, and crypto that are not used in the current lib/ tree.
Rust Native Layer And Shared Protocol

The Rust bridge crate exposes client, connection, file_transfer, share, simple, transfer, and webrtc modules. The generated Dart bindings are mostly thin wrappers around those exported Rust functions.
Pairing crypto derives a signaling key and SAS from a 32-byte secret via HMAC-SHA256 with simple "sig" and "sas" labels, generates URL-safe rendezvous ids and hex mailbox ids, and encrypts or decrypts signaling payloads with AES-256-GCM using a random 12-byte nonce prepended before base64 encoding.
The shared models crate contains both older registration/heartbeat DTOs and the blind-rendezvous mailbox DTOs used by the current connection flow. Some of the older session-oriented types remain in the repository even though the active server routes do not use them.
The Rust-side connection helper is the local pairing primitive. It generates the rendezvous id and shared secret, derives k_sig and sas, formats the invite link, and performs end-to-end signaling encryption and decryption.
The Rust client module keeps a process-local base URL and heartbeat interval in a mutex-protected static and exposes load, override, and reset functions, but the current Flutter app does not appear to consume that state.
The Rust webrtc module manages one data-channel-oriented peer connection per connection id. It registers codecs and default interceptors, filters out loopback and link-local ICE addresses, creates negotiated control and file_transfer channels, attaches data-channel handlers, and emits a queue of events that Dart later drains.
That Rust WebRTC layer handles offer/answer creation, remote-answer installation, ICE candidate addition, control-message sending, late renegotiation messages, session-close and ack messages, ping/pong messages, and file-channel I/O. Its native control-message parser recognizes base WebRTC renegotiation, file-transfer prompts, and session-liveness messages; screen-share control messages are passed through as generic text and interpreted later in Dart.
The share module is intentionally thin. It validates share configuration, checks that the control channel exists, and records active share state per connection, but the actual source enumeration, display capture, share media peer connection, and adaptive quality loop live on the Flutter side.
The active native file-transfer implementation is the actor-based one in api/file_transfer.rs. It uses a per-connection actor, a JSON control protocol (metadata, accept, reject, cancel, eof), bounded Tokio channels for background send work, and buffered-amount watermarks on the WebRTC file channel for backpressure.
That file-transfer actor hashes the outbound file with SHA-256 before sending, enforces a size cap, waits for explicit acceptance with a timeout, writes inbound bytes to a temporary file, verifies integrity on EOF, and then moves the file to a unique destination name.
The simple bridge is still just a small demo/scaffolding surface: it stores a short in-memory greeting buffer and initializes tracing.
Server Side

The signaling server workspace contains the main entrypoint, configuration loader, Axum router, Redis repository, and rendezvous service.
Configuration is environment-driven. The code requires SIGNALING_PUBLIC_URL, defaults the listen socket to 127.0.0.1:8080, defaults Redis TLS enforcement to on, supports a Redis key prefix, and exposes mailbox TTL, rendezvous TTL, and websocket push-buffer settings. The config struct still carries some older session-oriented and Redis-encryption fields that the active blind-rendezvous service does not consume directly, and the checked-in docker-compose file sets SIGNALING_ROOM_TTL_SECS even though the current server code never reads that variable.
The request router is intentionally small. It serves /, /health, /connection/init, /connection/join, /connection/send, /connection/recv, /connection/close, and /ws/:mailbox_id. Websocket fan-out is handled by a small in-process broadcast hub that publishes the same JSON payloads the HTTP handlers just wrote to Redis; it is not Redis Pub/Sub.
The rendezvous service is the heart of the server. init_connection creates an initiator mailbox and stores the rendezvous-token mapping. join_connection consumes the token, creates the responder mailbox, links the pair, and pushes an empty join marker into the initiator mailbox. send_message appends opaque ciphertext to the peer mailbox. recv_messages returns stored mailbox history. close_connection deletes both sides of a pair. A verify_mailbox helper exists, but it is not currently wired into any route.
Redis access is straightforward key/value plus list storage. Mailbox metadata is stored as JSON with TTL, rendezvous tokens are single-use mappings, and mailbox messages are appended to Redis lists. The server has no other persistence layer. Reads do not drain the message list, so the client de-duplicates between fetched history and pushed events on its own.
Error mapping is deliberate: invalid tokens and missing mailboxes become 404, expired sessions become 410, and already-paired or peer-missing cases become 409. That matches the client’s link-refresh and reconnect logic.
Frameworks, Tools, And Build Surface

Flutter and Dart provide the UI, onboarding, settings, share-sheet integration, and the screen-share media path. flutter_rust_bridge generates the Dart/Rust glue. flutter_webrtc is used for display capture, the screen-share media connection, and remote media rendering, while HTTP and websocket packages handle signaling transport. Shared preferences and file-system packages handle saved settings and file UX.
Rust covers the shared crypto helpers, the signaling server, the data-channel-oriented WebRTC session, and the file-transfer actor. On the server side the notable crates are axum, tokio, redis, serde, tracing, and thiserror. On the client/native side the main crates are webrtc, tokio, serde, tracing, once_cell, and sha2, with aes-gcm, hmac, base64, and uuid coming from the shared crate.
Deployment uses Caddy as the public HTTPS edge, Redis as the rendezvous store, and an optional coturn container for NAT traversal. In the checked-in compose file, coturn defaults to STUN-only; TURN needs extra env configuration before it becomes a real relay.
Packaging includes the Windows installer, which wraps the Flutter Windows release output into an executable installer.
